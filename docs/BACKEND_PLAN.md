# План бэкенда GiftMoney

Статус 31.10.2026: Telegram-авторизация размещена на Render + Neon, фронт на
Vercel. Пользователь подтвердил имя/аватарку и реальный вход из Telegram.
Проверки: 37 тестов авторизации, браузерная интеграция, PostgreSQL smoke test
локально с Neon и в CI. Секреты исключены из Git.

Текущая задача: общий сохраняемый тестовый инвентарь для профиля, обмена
и залога. Реальные Telegram-подарки и финансовый учёт ещё не подключены.
Изменения тестовых подарков должны сохраняться и синхронизироваться между
разделами; операции явно обозначены тестовыми.

Реализовано на этом этапе: таблицы экземпляров/инициализации/квитанций операций,
общий API инвентаря, пять стартовых подарков один раз на пользователя,
тестовые добавление/обмен/вывод, резерв и возврат подарка. Владение проверяет
сервер. Запросы с повторным ключом не повторяют действие; сервер возвращает
актуальный снимок. Резерв и вывод сериализованы блокировкой пользователя.
Фронт использует общий провайдер и обновляется при фокусе окна.
Проверки: 63 локальных теста; облачная PostgreSQL — идемпотентность и гонка
вывода с залогом; браузер — общие подарки, независимый выбор каталога и
экземпляра, обновление после внешнего изменения, сохранение после reload.
Финансовые условия демо-займа перенесены на сервер: сроки и суммы сохраняются,
старые резервы без выдачи денег возвращаются бесплатно, без создания долга.

Следующий реализованный блок: DEMO_TON wallet с двойной записью, защищёнными
остатками, сохраняемой однократной наградой, тестовыми пополнением/выводом
и историей. Баланс профиля и хедеров больше не хранится в HomePage.
Денежные условия демо-залога используют этот журнал. Настоящие платежи
и приём реальных Telegram-подарков пока не подключены.
См. docs/DEMO_WALLET.md. Проверки PostgreSQL включают конкурентные списания,
получение награды и отказ при нарушении баланса проводок.

Серверный блок займов: выдача, полное погашение, оплата процентов, пакетное
продление и автоплатёж; защита владения, повторов и конкурентных списаний.
Условия фиксированы демонстрационными тарифами, не рыночной оценкой.
Автоплатёж выполняется при работе API и догоняется после пробуждения Render;
для production нужен устойчивый планировщик. См. docs/DEMO_LOANS.md.
Стартовый экран скрывает авторизацию и первоначальную загрузку всех данных;
снимки инвентаря/баланса/займов защищены общей монотонной revision.

## Работа команды

Серверный демо-обмен переведён на сохраняемые котировки: источник sample,
настраиваемая наценка, ограниченный срок цены и атомарная замена подарков
с расчётом доплаты/остатка через общий журнал. Старый бесплатный обход
demo-exchange закрыт. Реальный источник цен и исполнение внешней доставки
остаются отдельными интеграциями; см. docs/DEMO_TRADES.md.

До появления заказчика используется GiftProvider-заглушка. Режим demo
сохраняет текущие тестовые операции, disabled блокирует выдачу подарков и
новых займов без удаления данных. Реального адаптера пока нет; подключение
подарков не блокирует независимую работу над учётом и серверными сценариями.
Контракт, ограничения и порядок замены описаны в docs/GIFT_PROVIDER.md.

- Основной агент: архитектура, реализация, интеграция и ведение этого плана.
- Архитектурный ревьюер: проверяет план, инварианты, изменения схемы и итог каждого этапа.
- QA-агент: проверяет критерии этапа, пишет/запускает независимые проверки при реализации.
- Замечания проходят через основного агента. Этап закрывается после проверки результата.
- Агенты работают во время активной задачи, не являются постоянными фоновыми сервисами.
- Параллельные изменения получают разные файлы; аудит выполняется по конкретной версии кода.

## Предлагаемая структура

Первый вариант: модульный сервер на Python/FastAPI, PostgreSQL, отдельный worker.
Выбор стека предварительный; версии и API проверяются перед реализацией.
Redis добавляется только при конкретной потребности в очереди/ограничении запросов.
Существующий React/Vite-фронт сохраняется; backend размещается отдельно от Vercel-фронта.

```text
backend/
  app/
    api/             # HTTP, зависимости авторизации, ошибки
    modules/         # users, gifts, ledger, trades, loans, payments, referrals
    integrations/    # Telegram, TON, платёжный провайдер
    workers/         # задания, повторные попытки, сверка операций
    db/              # подключение, модели
    core/            # настройки, логирование
  migrations/
  tests/
```

## Этапы

  Результат: схемы операций и список согласованных правил. Проверить доступные
  Telegram API для приёма, хранения, передачи и ограничений подарков.
- [ ] 1. Каркас: конфигурация окружений, API /health, PostgreSQL, миграции,

- [ ] 2. Telegram-авторизация: серверная проверка initData и срока действия,

- [ ] 3. Единый каталог и инвентарь: коллекции/модели/символы/фоны, владение,
  состояния доступности, поиск, фильтры, сортировка и пагинация.
- [ ] 4. Денежный учёт: журнал проводок, доступный/зарезервированный баланс,

  Суммы TON хранятся целым числом nanoTON; float запрещён для расчётов.
- [ ] 5. Ввод/вывод: адаптеры провайдеров, проверенные входящие события,
  резервирование вывода, повторная доставка, ручная сверка неоднозначного результата.
- [ ] 6. Обмен: серверная котировка со сроком действия, атомарный резерв
  подарков и денег, подтверждение, исполнение, отмена и восстановление.
- [ ] 7. Залог: серверные условия/котировка, резерв подарка, выдача займа,
  погашение, проценты, продление, автоплатёж и обработка просрочки.
- [ ] 8. Рефералка: связь приглашения, начисление от подтверждённой комиссии,

- [ ] 9. Подключение React к API: общий пользователь/баланс/инвентарь,
  серверные статусы вместо таймеров, восстановление после перезагрузки,
  обработка ошибок и ожидания. Моки остаются только в явном demo-режиме.
- [ ] 10. Итоговая проверка: конкурентные операции, сбои внешних API,

## Общие критерии

- Пользователь получает доступ только к своим операциям и подаркам.
- Повтор запроса или события не меняет деньги/владение повторно.
- Один подарок нельзя одновременно обменять, вывести и заложить.
- Доступный баланс не становится отрицательным; сумма проводок сверяется.
- Внешние вызовы не выполняются внутри долгой DB-транзакции. Задания на
  отправку сохраняются надёжно вместе с изменением состояния (outbox).
- После таймаута неизвестный внешний результат сначала сверяется, а не повторяется вслепую.
- Каждый этап имеет миграции, значимые тесты и проверку ревьюера.
- Секреты и пользовательские сессии исключены из Git и логов.

## Что нужно согласовать до соответствующего этапа

- Где физически хранятся подарки: бот, аккаунт-хранитель, внешний сервис;
  кто предоставляет учётные данные и как подтверждается факт передачи.
- Источник рыночных цен, период обновления, комиссия обмена и минимальные суммы.
- Способы пополнения/вывода, провайдер, сеть, подтверждения, комиссии и лимиты.
- Условия займа: оценка обеспечения, проценты, сроки, продление, просрочка,
  судьба обеспечения, момент и повторные попытки автоплатежа.
- Правила рефералки и отмены начислений при неисполненной операции.
- Доступ администратора, ручная обработка спорных/зависших операций.

## Замечания ревью

Первый проход выполнен: архитектура — Bernoulli; QA — McClintock.
Замечания внесены ниже; это проверка плана, а не готового бэкенда.

### Дополнения архитектуры

- До интеграции составить датированную матрицу возможностей Telegram API и
  подтвердить выбранный сценарий в тестовом окружении. Неопознанные поступления
  изолировать до сверки; получатель вывода должен быть проверен.
- Разделить владельца подарка и физического хранителя. Внешний ID уникален,
  активный резерв общий для всех модулей и защищён ограничениями БД.
- Использовать неизменяемую двойную запись по каждому активу: средства пользователей,
  резервы, казначейство, займы, проценты, комиссии и реферальные обязательства.
  Исправления выполняются обратными проводками; учёт сверяется с внешними активами.
- Ключ идемпотентности связан с пользователем и хешем параметров: повтор возвращает
  исходный результат, другой payload с тем же ключом отклоняется. Дедупликация
  платежа требуется и по внешнему transfer/payment ID, а не только event ID.
- Определить обработку поздних/частичных платежей, возвратов и событий не по порядку.
  Неопределённый результат внешней отправки сохраняет резерв до сверки.
- У котировки фиксируются пользователь, версии подарков, цены, комиссии и срок.
  Согласовать модель обмена с собственным каталогом или между пользователями,
  судьбу переплаты и политику частично исполненной внешней доставки.
- В демо extend добавляет 14 дней с комиссией 0.01 TON, а payInterest — исходный
  срок без комиссии. Единое правило нужно согласовать до этапа 7.
- Worker: устойчивое расписание, аренда задания, восстановление после сбоя,
  ограниченные повторы с задержкой, очередь ручного разбора. Истечение аренды
  не разрешает повторять уже отправленную внешнюю операцию без сверки.
- Предусмотреть историю/статус операций, журнал действий администратора,
  остановку выдачи/выводов и оповещения при расхождении учёта.

### Проверки, закрывающие этапы

- Авторизация: поддельные, просроченные и будущие initData; подмена ID чужого
  ресурса; истёкшая сессия; отсутствие dev-входа в production.
- Деньги: 1 TON и два одновременных вывода по 0.75 — проходит один;
  20 повторов одного запроса — одна проводка; другой payload отклоняется.
  Один nanoTON сохраняется точно; неверные и переполняющие суммы отклоняются.
- Платежи: 20 повторов callback и разные event ID одного платежа дают одно
  зачисление; неверные подпись, сеть, актив и получатель не дают зачисления;
  события не по порядку не откатывают финальный статус.
- Сбой worker после принятия перевода провайдером восстанавливается сверкой;
  однозначный отказ освобождает резерв один раз, таймаут сохраняет его.
  Частичный вывод подарков не отправляет успешные элементы повторно.
- Конкурентные обмен/вывод/залог одного подарка дают одного победителя.
  Недоступный элемент атомарного обмена не меняет остальные активы.
  Истёкшие/чужие котировки и дубликаты ID отклоняются.
- Займы: повтор создания выдаёт principal один раз; погашение, продление,
  автоплатёж и просрочка не списывают дважды и не освобождают залог повторно.
  Проверить границы срока серверными часами и перезапуск worker.
- Реферальное вознаграждение забирается один раз; политика обратного начисления
  при отмене операции проверяется после согласования правил.
- После операции все разделы и вторая сессия видят одинаковые данные.
  Перезагрузка и закрытие модалки восстанавливают реальный статус операции.
- Production не содержит чередования успеха/ошибки, зачислений по таймеру,
  стартовых 5 TON рефералки, фиктивного кошелька и локального автоплатежа.

Для этапов 4/6/7 обязательны конкурентные тесты с настоящим PostgreSQL;
для 5 — тестовый провайдер и внесение сбоев; для 9 — браузерные проверки
перезагрузки и двух сессий. Неопределённые бизнес-правила блокируют только
зависимые сценарии, пока независимые части продолжают реализовываться.
